My project is an interactive Java/JavaFX simulator for 3D drone localization using multistatic radar geometry: the user configures one transmitter and multiple receivers, moves a drone across a 3D trajectory, simulates bistatic range measurements, estimates the drone's position, and compares it against ground truth. I treat AI coding assistants not as oracle generators, but as high-velocity, junior pair-programmers. The overarching governance rule across the project lifecycle is strict: I define requirements, every AI proposal must be verified against independent oracles and automated tests, and I must be able to derive and explain every single line during the live evaluation.

1. Prompt Engineering: Principles, Discipline & Guardrails

To eliminate hallucinations and avoid fragile code dumps, I operationalized a structured prompt engineering methodology (tracked under version control in prompts/PROMPT-LOG.md):

  • Phase Separation (Understanding & Planning Before Code): Before touching any file, prompts enforce an architectural audit against the proposal and design doc. For example, Prompt P1 asked the AI to analyze codebase completeness before proposing modifications. This exposed that while 76 tests passed, the localization model suffered an 80–115 m error on noiseless data that was silently masked by superficial assertions.
  • Explicit Verification Oracles: Prompts never request open-ended "improvements". They enforce quantifiable constraints: "Pass all 111 JUnit tests; noiseless reference cases must yield <1.0 mm localization error; compute condition numbers". Without explicit oracles, AI outputs tend towards syntactically valid but physically erroneous baselines.
  • Granular Scope & Commit-Sized Units: Every prompt is scoped strictly to a single architectural concern (build script compatibility, Levenberg–Marquardt solver, geometry validation, or package modularization). This keeps diffs auditable and simplifies rollback.
  • "Say what to do first, then I decide": I enforce human-in-the-loop control (e.g., "say me what is there to do then i will say to do or not"). The assistant drafts proposals and commit breakdowns; I review and approve before execution.
  • Explain the Underlying Mathematics: Whenever numerical routines (e.g., Levenberg–Marquardt damping, analytic Jacobians, condition numbers) are generated, I require step-by-step mathematical justifications so I master the underlying physics for viva defense.
Prompt Checklist Enforced in Repo: (1) Provide file context & design doc anchors; (2) Require diagnosis & plans before code edits; (3) Single concern per prompt; (4) Define exact mathematical tolerance (<1 mm); (5) Explicitly state forbidden edits (e.g. preserve interfaces); (6) Demand root-cause explanations; (7) Version-control prompts in PROMPT-LOG.md.

2. Systematic Debugging: Reproduce, Measure, Isolate & Guard

I employ a disciplined hypothesis-driven debugging cycle: Reproduce with a minimal harness → Measure quantitative error → Isolate root cause → Minimal targeted fix → Add regression guard. Four representative bugs solved during development:

Symptom & Context Isolation & Root Cause Analysis Engineering Fix Applied Regression Guard & Oracle
~100 m localization error on noiseless data; all 76 tests falsely green. Ran CLI with 3/4/5 receivers. Tests passed because assertions merely checked isFinite(error). Root cause: naive gradient descent forced Z to 500 m with ad-hoc weighting. Replaced with Levenberg–Marquardt non-linear least squares solving bistatic range ellipsoids with analytic Jacobians (BaselineLocalizationModel). Synthetic noiseless test suite asserting position error < 1.0 mm (achieved 0.0000 m).
Build Crash: Unsupported class file major version 70 on ./gradlew. Major version 70 corresponds to Java 26 preview classfiles. Gradle 8.10 wrapper lacked Java 26 compatibility, failing before compilation. Upgraded the project Gradle wrapper to v9.3.0 in gradle-wrapper.properties. Committed wrapper binary & verified clean CI build on fresh JDK 26 environment.
Off-by-One Time Step: Last trajectory record missing from simulation run. Traced time accumulator: t += dt accumulated floating-point roundoff (0.1+0.1+0.1 = 0.30000000000000004 > 0.3), causing early loop termination. Refactored accumulator to integer index calculation: t = i * dt across discrete step counts. Unit test: duration 0.3 s at 0.1 s step strictly produces 4 discrete trajectory states.
False Failure in Test: "Target on ground unstable" test failed unexpectedly. Built diagnostic harness printing residual and matrix condition number across heights 0–100 m. Position estimate was 100% correct, but condition number spiked (1.9×107 vs 33). The test's premise was faulty, not the algorithm. Corrected test assertion to verify condition number warning rather than rejecting position. Maintained test verifying geometry health metrics without masking numerical warnings.

3. Version Control (Git): Tracking Code, Prompts & History

Git serves as our immutable audit trail for both code evolution and AI interaction telemetry, adhering to professional standards:

  • Dual Tracking (Code & Prompts): In addition to source code, all raw developer prompts, outcomes, verification steps, and improved formulations are versioned in prompts/PROMPT-LOG.md. Every prompt directly references the commit hash it produced.
  • Conventional, Metric-Driven Commits: Commit messages strictly follow the type(scope): summary standard (e.g., fix(localization): replace gradient descent with Levenberg-Marquardt solver). The body documents why the change occurred and the exact verification metric achieved (e.g. "error reduced from 100m to 0.0000m on noiseless baseline; tests expanded from 76 to 90").
  • Safe Feature Branching: Risky algorithmic work is isolated on dedicated branches (e.g., mid-demo-fixes). Only after the complete test suite passes and manual CLI sanity checks succeed is main fast-forwarded.
  • Preserving History across Major Refactorings: When modularizing the monolithic 21-class model package into the 8 architectural packages prescribed by Phase 3 Design Doc §1.3, all file relocations were executed via git mv (27 clean file renames). This ensures git log --follow retains complete line-by-line historical provenance.
  • AI Transparency & Authorship: Commits generated with AI pair-programming assistance include explicit Co-Authored-By trailers, guaranteeing honesty and accountability. Git author configuration was validated to ensure all commits link to my primary GitHub identity (shervan0714).

4. Software Quality: Testing, Refactoring & Comprehensive Documentation

Rigorous Testing Strategy (111 Automated JUnit Tests)

  • Comprehensive Test Suite: Test coverage expanded from 76 to 111 automated JUnit tests, with dedicated unit test classes covering every single module defined in the Design Document: linear algebra (Vector3D, Matrix3x3), trajectory models, measurement models, BaselineLocalizationModel, GeometryValidator, experiment pipeline, persistence, and GUI transformation logic.
  • Ground Truth Oracle: Because the simulator controls true drone kinematics, synthetic noiseless benchmark scenarios (3, 4, and 5 receivers, wide baseline, mast elevations) must reconstruct the true 3D coordinates within 1.0 mm. Current baseline achieves 0.0000 m error.
  • Boundary & Degeneracy Verification: The test suite rigorously stresses failure conditions: under-constrained receiver sets (<3 receivers), collinear receiver baselines, duplicate receiver IDs, physically impossible ranges, and ill-conditioned sensor planes. The system returns explicit status codes (UNDER_CONSTRAINED, INVALID_INPUT, DEGENERATE_GEOMETRY) rather than silent erroneous numbers.
  • Decoupled UI Testability: GUI business logic is isolated into pure, headless Java classes: ScenarioConfig (maps input controls to validated scenario domain objects) and SceneTransform (maps East/North/Up engineering coordinates to JavaFX camera frames). This enables automated unit testing without requiring an active display server.

Architecture Refactoring & Clean Code

All refactoring operations are strictly behavior-preserving and regression-guarded. Monolithic prototype classes like RadarPhysics were cleanly decomposed into modular, extensible interfaces (MeasurementModel and LocalizationModel). Dead, disconnected prototype code (such as unused parameter forms and frame loops) was excised, decoupling the simulator engine from JavaFX presentation.

Documentation Architecture

  • README.md: Complete quick-start guide, build instructions, CLI/GUI operational parameters, coordinate frames, and architecture overview.
  • docs/PROJECT-STRUCTURE.md: Exhaustive architectural inventory mapping all 45 source files to their design doc modules with clear guidance on "where to change what" (vital for the live code modification task).
  • docs/MID-DEMO.md: Complete 5-minute evaluator demonstration walkthrough and an honest declaration of 12 known gaps (e.g., synthetic noise models, orientation degree inputs, placeholder radar cross-section power equations).
  • docs/WEEKLY-LOG.md: Continuous weekly engineering journal recording technical decisions, commit logs, and milestone progress.
Live Code Modification Readiness: The codebase is decoupled into clean interfaces with 111 fast-running unit tests (<2 seconds total execution). Any live TA task (e.g., adding a receiver filter, modifying noise injection, or adding an export column) can be quickly implemented in its dedicated module and instantly verified via automated regression tests.
