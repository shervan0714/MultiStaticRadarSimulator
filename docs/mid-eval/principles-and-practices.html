Principles & Practices — How I Build My Project with AI

E. Sai Shervan (CS24B073) · CS5013 Programming with AI · Mid-evaluation, October 2026
Project: Interactive Multistatic Radar Simulator for 3D Drone Localization · Stakeholder: Dr. Giridhar K (EE) · Repo: github.com/shervan0714/MultiStaticRadarSimulator

My project is a Java/JavaFX simulator: you place a transmitter and several receivers, move a drone along a trajectory, simulate the radar measurements, estimate the drone's 3D position, and compare it with the true position. I use an AI coding assistant (Claude Code, running inside my repository) for much of the implementation. My rule is that the AI is a fast collaborator, not an authority: I decide what gets built, every change has to pass a check I can run myself, and I must be able to explain every line. This document describes how I apply that rule.

1. Prompt engineering

Looking back at my prompt history (kept in prompts/PROMPT-LOG.md), these are the principles that worked, and the ones I learned from my weaker prompts.

  • Understanding before code. My most useful prompt asked the assistant to read my proposal, design doc and code and tell me how far the project really was, before changing anything. It built and ran everything and found that localization was 80–115 m off on noiseless data, while all 76 tests still passed — because the tests only checked that the error was a finite number. Asking for code first would have built more on a broken base.
  • Plan, then approve. I ask for a plan split into commit-sized steps and approve it (e.g. "say me what is there to do then i will say to do or not"). This keeps the scope mine and forces me to read each proposed change.
  • One concern per prompt. Each request maps to one commit (build fix, solver, tests, ID bug…). Small steps are easier to verify and to undo.
  • State the check, not just the task. "Tests must pass", "noiseless cases within 1 mm", "show me the app running". Without a check I can't tell good output from plausible-looking output.
  • Be specific about symptoms. One weak prompt — "use shervan0714 github not karthiks" — named a symptom without saying where I saw it, so the assistant had to investigate everything. (It still found a real issue: my commits were not linked to my GitHub account because of the commit email.) Now I say what I saw, where, and what I expect.
  • Ask "why". When I don't understand a result (e.g. why there were empty folders, why the solver needs several starting points), I ask before accepting it. I will be asked to explain it in the viva.

The domain mathematics is not taken from the AI as authority: the stakeholder's formulation will decide the final model, and the current baseline is checked against known ground truth. Sample prompts, with how I would improve them, are in the appendix.

2. Debugging

I follow the same loop for every bug: reproduce → measure → isolate → form a hypothesis → minimal fix → add a regression test → record it. Four real cases from this project:

SymptomHow it was isolatedRoot cause → fixRegression guard
Estimates ~100 m off on noiseless data, yet all tests green Ran the CLI for 3/4/5 receivers to measure the error; read the tests — they asserted only isFinite(error). Error should be ~0 with perfect data, so the solver itself was wrong. Power-weighted guess + finite-difference gradient descent with z forced to 500 m. Replaced with least squares on bistatic-range ellipsoids (Levenberg–Marquardt, analytic Jacobian). Reference scenarios must match truth within 1 mm
gradlew test crashed: "Unsupported class file major version 70" Version 70 = Java 26 class files; the wrapper pinned Gradle 8.10, which cannot run on Java 26. Confirmed by running the same build with a cached Gradle 9.3. Upgraded the wrapper to 9.3.0. README build steps; wrapper committed
Last sample sometimes missing from a run Time was accumulated as t += dt; with dt = 0.1, 0.1+0.1+0.1 = 0.30000000000000004 > 0.3, so the loop stopped early. Compute time from the step index: t = i · dt. Test: duration 0.3, step 0.1 → 4 records
New test "target on the ground is unstable" failed Wrote a small probe printing estimate, residual and condition number for heights 0–100 m. The estimate was correct; only the condition number exploded (1.9×107 vs 33). The test's assumption was wrong, not the code. Rewrote the test to check the warning signal (large condition number). Test kept, with the corrected expectation

Two lessons: a test suite that cannot fail gives false confidence, and when a test fails I first decide whether the code or the expectation is wrong. For the GUI, where tests cannot see the screen, I also check rendered screenshots (that is how an upside-down Y axis in the 3D view was caught).

3. Version control (Git) — for code and prompts

  • Small, purposeful commits with type(scope): summary messages (fix(localization), test, refactor, docs) and a body that says why and what was measured. My early message "rewrote localization math…, accuracy is way better now" claimed an improvement that was never measured (the error was still ~100 m); now messages report numbers.
  • Branch, then fast-forward. Work happens on mid-demo-fixes; after the full test suite passes, main is fast-forwarded and pushed, so main always builds.
  • History is preserved. When I split the 21-class model package into the design doc's modules, files were moved with git mv (27 renames), so git log --follow still shows each file's history.
  • AI help is visible. Commits made with the assistant carry a Co-Authored-By trailer, so the history is transparent about where AI was involved.
  • Prompts are versioned with the code. prompts/PROMPT-LOG.md records each prompt verbatim with its date, goal, outcome, how it was checked, and the commit hash it produced, plus a rewritten "better version". It is committed alongside the code changes, so prompt → change → verification can be traced.
  • Hygiene. .gitignore keeps build output out; .gitattributes fixes line endings for scripts. I also fixed my commit email so commits link to my GitHub account (older commits used an address not on my account).

4. Testing, refactoring and documentation

Testing

  • 111 JUnit tests (up from 76), with at least one test class per design doc module: vectors and 3×3 maths, trajectory, measurement, localization, geometry validation, experiment runner, evaluation, persistence, and the GUI's logic.
  • Ground truth as the oracle. Because the true drone position is known at every step, noiseless reference scenarios (3, 4 and 5 receivers, wide baseline, close range, elevated transmitter) must reproduce it within 1 mm.
  • Failure cases are tested too. Too few receivers, collinear sensors, duplicate IDs, physically impossible ranges and badly conditioned geometry must return an explicit status (UNDER_CONSTRAINED, INVALID_INPUT, …), never a silent wrong position.
  • Testable design. GUI logic that can be pure Java is pure Java (ScenarioConfig: form → scenario; SceneTransform: East/North/Up → JavaFX), so it is unit-tested without a display.

Refactoring

Refactors are behaviour-preserving and guarded by the test suite: the package restructure changed only packages and imports, and all 111 tests passed before and after. Unused code was removed (an unconnected ParameterPanel, a frame-by-frame loop that bypassed the experiment pipeline), and the coupled RadarPhysics class from the early prototype was split into replaceable MeasurementModel / LocalizationModel interfaces, as planned in the design doc.

Documentation

  • README.md — build/run steps, GUI and CLI usage, coordinate convention, architecture, verification, contact.
  • docs/PROJECT-STRUCTURE.md — what every file is for, and "where to change what".
  • docs/MID-DEMO.md — demo script and an honest list of 12 known gaps (e.g. noiseless measurements, placeholder power formula, stakeholder formulation not yet received).
  • docs/WEEKLY-LOG.md — weekly contributions, doubling as the change log; Javadoc records modelling assumptions (e.g. the "target above the sensors" choice for coplanar layouts).

Prompt checklist I now follow: (1) give context and point to files; (2) ask for understanding or a plan before code; (3) one concern per prompt; (4) state how the result will be checked; (5) say what must not change; (6) ask "why" until I can explain it; (7) log the prompt with the commit it produced.
